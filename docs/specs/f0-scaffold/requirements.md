# F0 Scaffold and tooling — Requirements

## Introduction

This spec creates the empty but production-shaped foundation of the `smart-appointments-web` repository: an Angular workspace with strict compiler settings, Tailwind v4 and Spartan/ui with a light/dark theme, linting, formatting and commit hooks, unit and end-to-end test runners, bundle budgets, a runtime-configurable container image served by nginx, a Docker Compose file, and a CI pipeline. It contains no feature screens.

It refines build phase F0 of the approved frontend plan. It has **no FR-ID**: the backend BRD (SmartAppointments `docs/requirements.md`) describes services, not tooling. The backend contract (the gateway on `http://localhost:5290`) is only consumed from F1 on; F0 merely makes the API origin configurable.

"Latest" below means the latest stable release at scaffold time; the versions actually chosen are recorded in `package.json` and in the README, not in this spec.

## Decisions

Approved with these decisions:

- **Brand accent is teal.** Exact shades are fixed in the design after a contrast check: teal-600 on white measures only 3.74:1, so it is used for focus rings, icons and large text, while filled buttons and text links use teal-700 (5.47:1 with white text) in light mode, and teal-400 (10.69:1 with zinc-950 text) in dark mode.
- The `pnpm size` gzip check stays alongside the Angular budgets.
- `style-src 'unsafe-inline'` is accepted as a known gap.
- The read-only root filesystem with the nginx-unprivileged base image stays.
- `.gitattributes` (LF enforcement) stays.
- The Sonnet subagent rule stays in CLAUDE.md.

## Requirements

### Requirement 1: Workspace and toolchain (no FR-ID)

**User Story:** As a developer, I want a reproducible Angular workspace, so that every machine and CI run builds with the same toolchain.

#### Acceptance Criteria

1. The repository root SHALL contain an Angular workspace generated by the latest stable Angular CLI, with standalone components only (no NgModules), plain CSS (`src/styles.css`) instead of SCSS, and the Vitest unit-test builder.
2. The package manager SHALL be pnpm. `package.json` SHALL declare it in the `packageManager` field (exact version), and `pnpm-lock.yaml` SHALL be committed. IF `npm install` or `yarn install` is run, THEN it SHALL be rejected by a `preinstall` guard (`only-allow pnpm`).
3. `.nvmrc` SHALL pin the current Node LTS major version, and `package.json` `engines.node` SHALL require that major or newer. CI and the Dockerfile build stage SHALL use that same major.
4. Angular, TypeScript and library versions SHALL float to the latest stable at scaffold time and SHALL be pinned by the lock file afterwards. Dependency upgrades after F0 are ordinary changes, not part of this spec.
5. The application SHALL be zoneless: `provideZonelessChangeDetection()` SHALL be registered in `app.config.ts`, and `zone.js` SHALL NOT appear in `package.json` or in the build `polyfills`.
6. `tsconfig.json` SHALL enable `strict`, `noImplicitOverride`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature` and `isolatedModules`, and `angularCompilerOptions` SHALL enable `strictTemplates`, `strictInjectionParameters` and `strictInputAccessModifiers`. `pnpm build` SHALL fail on a type error in a TypeScript file or in a template.
7. `package.json` SHALL define these scripts: `start` (`ng serve`, port 4200), `build`, `test` (single run), `test:watch`, `lint`, `format`, `format:check`, `typecheck`, `size` and `e2e`.
8. The `src/app` tree SHALL contain the empty layout folders `core/`, `shared/ui/` and `features/` (each with a `.gitkeep` or a real file), matching the plan's layout, and a root `App` component showing a placeholder page that renders the application name.

### Requirement 2: Styling, design tokens and theme (no FR-ID)

**User Story:** As a user, I want a consistent, accessible look that follows my system theme and lets me override it, so that the app is comfortable in any lighting.

#### Acceptance Criteria

1. Tailwind CSS v4 SHALL be installed with its CSS-first configuration (`@import "tailwindcss"` and an `@theme` block in `src/styles.css`); there SHALL be no `tailwind.config.js`.
2. Spartan/ui (brain and helm) SHALL be initialised with its CLI so that helm components land under `src/app/shared/ui/`, and at least one helm component (the button) SHALL be generated and rendered on the placeholder page to prove the toolchain.
3. `src/styles.css` SHALL define design tokens as CSS custom properties exposed through `@theme`: a neutral zinc scale for background, foreground, muted, border and ring; **one** brand accent (the teal scale) with its foreground; and radius and shadow tokens. Light values SHALL live on `:root` and dark values under a `.dark` class on `<html>` (class-based `@custom-variant dark`).
4. Foreground/background token pairs used for text SHALL meet WCAG 2.2 AA contrast (4.5:1 normal text, 3:1 large text and UI components) in both themes. The design records the measured ratios.
5. The Inter variable font SHALL be self-hosted through `@fontsource-variable/inter` (no request to Google Fonts or any other third-party origin) and set as the default sans font token.
6. A signal-based `ThemeService` SHALL expose the preference `system | light | dark`, defaulting to `system`. WHEN the preference is `system`, THEN the `dark` class SHALL follow `prefers-color-scheme` live. WHEN the user picks `light` or `dark`, THEN the class SHALL be set accordingly.
7. The preference SHALL be persisted per viewer in `localStorage` under a single key. IF `localStorage` throws or is unavailable (private window, blocked storage), THEN the app SHALL keep working with the in-memory preference and no uncaught error.
8. To avoid a flash of the wrong theme, a script in `index.html` SHALL apply the `dark` class from the stored preference or the system setting before the first paint (see Requirement 7.8 for how it coexists with the CSP).
9. The placeholder page SHALL include a theme toggle with an accessible name, a visible focus ring and a state announced to assistive technology (for example `aria-pressed` or a labelled menu), operable by keyboard.
10. WHILE the user has `prefers-reduced-motion: reduce`, the stylesheet SHALL disable non-essential transitions and animations globally.

### Requirement 3: Code quality gates (no FR-ID)

**User Story:** As a maintainer, I want style and commit rules enforced automatically, so that the history and code stay consistent without review effort.

#### Acceptance Criteria

1. angular-eslint (flat config) with typescript-eslint SHALL be configured with the recommended and template-accessibility rule sets, plus `prefer-on-push-component-change-detection`, `prefer-standalone`, `prefer-inject` and `@typescript-eslint/no-explicit-any` as errors. `pnpm lint` SHALL pass on the scaffold with zero warnings (`--max-warnings 0`).
2. Prettier SHALL format TypeScript, HTML, CSS, JSON and Markdown with the `prettier-plugin-tailwindcss` class sorter. `pnpm format:check` SHALL pass on the scaffold and fail on an unformatted file.
3. Husky SHALL install on `pnpm install` (`prepare` script). A `pre-commit` hook SHALL run lint-staged (ESLint `--fix` and Prettier on staged files only). A `commit-msg` hook SHALL run commitlint.
4. commitlint SHALL enforce Conventional Commits (`@commitlint/config-conventional`). WHEN a commit message is `fix stuff`, THEN the commit SHALL be rejected; WHEN it is `feat(core): add theme service`, THEN it SHALL be accepted.
5. `.editorconfig` SHALL set UTF-8, LF line endings, two-space indent and a final newline. `.gitattributes` SHALL enforce LF for text files, so that Windows checkouts do not break the shell script in `docker/`.
6. Hooks SHALL NOT run in CI (`HUSKY=0`), because CI runs the same checks as explicit steps.

### Requirement 4: Unit and end-to-end test runners (no FR-ID)

**User Story:** As a developer, I want test runners working from day one, so that every later feature is built test-first.

#### Acceptance Criteria

1. `pnpm test` SHALL run Vitest once through the Angular builder in a DOM environment and exit non-zero on a failure. `pnpm test:watch` SHALL run it in watch mode.
2. Angular Testing Library SHALL be installed and used by at least one sample test.
3. The scaffold SHALL include at least these unit tests, all passing: (a) the root `App` renders the application name; (b) `ThemeService` applies and removes the `dark` class for each preference, follows a simulated `prefers-color-scheme` change in `system` mode, and survives a throwing `localStorage`; (c) the runtime-config loader cases of Requirement 6.
4. `pnpm test -- --coverage` SHALL produce a coverage report; no minimum threshold is enforced in F0 (see Known gaps).
5. MSW SHALL be installed with a `src/testing/` folder holding the shared server setup (`setupServer`) wired into the Vitest setup file with an empty handler list and `onUnhandledRequest: 'error'`, so an unmocked network call fails a test.
6. Playwright SHALL be installed and configured (`playwright.config.ts`) with a Chromium project only, `baseURL` from `E2E_BASE_URL` (default `http://localhost:4200`), a `webServer` entry that starts the app when no URL is supplied, `retries: 2` and `trace: 'on-first-retry'` in CI, and tests under `e2e/`.
7. The e2e suite SHALL contain one smoke test: WHEN the app is opened, THEN the page title and application name are visible; WHEN the theme toggle is activated, THEN `<html>` gains the `dark` class and it is still present after a reload; WHEN `/config.json` is intercepted to return `500`, THEN the configuration error page of Requirement 6 is shown. The smoke test SHALL NOT need the backend.
8. `pnpm e2e` SHALL run the suite headless; the README SHALL state the one-time `pnpm exec playwright install chromium` step.

### Requirement 5: Bundle budgets (no FR-ID)

**User Story:** As a user on a slow connection, I want the app to load quickly, so that the first screen appears without a long wait.

#### Acceptance Criteria

1. The production configuration in `angular.json` SHALL set `budgets` of: `initial` warning `500kB`, error `700kB`; `anyComponentStyle` warning `4kB`, error `8kB`.
2. The initial limits SHALL be justified in the design by the plan's target of **under 250 kB gzipped for the initial bundle**. Angular budgets measure uncompressed size, and minified JavaScript compresses roughly 3 to 3.5 times, so 700 kB raw is about 200 to 235 kB gzipped: the ceiling stays under 250 kB gzipped while leaving headroom for F1 to F5. The 500 kB warning makes growth visible early.
3. CI SHALL additionally fail IF the gzipped total of the files listed as initial in the build output exceeds 250 kB, measured by a script in `scripts/` (`pnpm size`), so the real target is enforced and the raw budget is only a proxy.
4. `pnpm build` on the scaffold SHALL produce an initial bundle well below both warning thresholds, and the `pnpm size` result SHALL be printed in the CI log.
5. `app.routes.ts` SHALL exist and declare at least one lazy-loaded placeholder route, so that the convention "routes after F0 are lazy" is in place.

### Requirement 6: Runtime configuration (no FR-ID)

**User Story:** As an operator, I want to point one built image at any API origin when the container starts, so that the same artefact serves every environment and a misconfiguration is obvious.

#### Acceptance Criteria

1. The app SHALL fetch `/config.json` (relative to the document origin, `cache: 'no-store'`) in a `provideAppInitializer` before the application renders, and expose the parsed value through an injectable `AppConfig` token of shape `{ apiBaseUrl: string }`.
2. The `config.json` served by `ng serve` SHALL contain `{ "apiBaseUrl": "http://localhost:5290" }` and be copied to the build output as an asset, so local development needs no extra step. The container replaces it at start (Requirement 7.4).
3. WHEN `apiBaseUrl` is an absolute `http` or `https` URL, THEN the loader SHALL accept it and normalise it to its origin (trailing slash, path, query and fragment removed).
4. IF `/config.json` cannot be fetched (network error, non-2xx status, no answer within 5 seconds), is not valid JSON, lacks `apiBaseUrl`, or `apiBaseUrl` is blank or not an absolute `http(s)` URL, THEN the app SHALL NOT bootstrap its normal shell and SHALL instead render a standalone **configuration error page** (plain HTML and inline styles, not depending on Tailwind, Spartan or the router, so it works even when the rest failed). The page SHALL state in plain language that the application is not configured, name the problem (for example "config.json returned 404" or "apiBaseUrl is not a valid URL"), and offer a "Try again" button that reloads the page.
5. The configuration error page SHALL never be blank, SHALL set the document title to `Configuration error`, SHALL be keyboard operable, and SHALL NOT display the response body.
6. The loader SHALL be a pure function (`loadConfig(fetchFn)` returning a discriminated result) covered by unit tests for each case in criteria 3 and 4.
7. No environment-specific value SHALL be compiled into the bundle: `grep -r "localhost:5290" dist/` SHALL find nothing in the production build output other than `config.json` itself.

### Requirement 7: Container image and nginx (no FR-ID)

**User Story:** As an operator, I want a small, hardened image that serves the SPA correctly, so that deep links work, caching is right and the browser enforces a restrictive security policy.

#### Acceptance Criteria

1. A multi-stage `Dockerfile` at the repository root SHALL build in a `node:<LTS>-alpine` stage (pnpm through corepack at the `packageManager` version, `pnpm install --frozen-lockfile` run before copying the sources so a code change does not invalidate the dependency layer) and run on `nginx:alpine` (a pinned tag). The final image SHALL contain only the built output, the nginx configuration and the entrypoint script: no Node, sources or `node_modules`.
2. A `.dockerignore` SHALL exclude at least `node_modules`, `dist`, `.git`, `.angular`, `coverage`, `playwright-report`, `test-results` and `.env`.
3. The final image SHALL run nginx as a **non-root** user, listening on an unprivileged port (`8080` inside the container), with pid, temp and log paths writable by that user (the `nginxinc/nginx-unprivileged` image or an equivalent configuration). `docker run --rm <image> id -u` SHALL NOT print `0`.
4. The container entrypoint (`docker/40-config.sh`, run from `/docker-entrypoint.d/`) SHALL render `/config.json` from a template by substituting `API_BASE_URL` with `envsubst`. IF `API_BASE_URL` is unset or empty, THEN the container SHALL still start and serve a `config.json` with an empty `apiBaseUrl`, so the SPA shows the configuration error page rather than the container crash-looping. The script SHALL write valid JSON even if the value contains quotes or backslashes (JSON-escaped).
5. The same entrypoint SHALL derive the CSP `connect-src` origin from `API_BASE_URL` (scheme, host and port only) and write it into the nginx configuration at start. IF `API_BASE_URL` is not a valid origin, THEN `connect-src` SHALL fall back to `'self'` only.
6. nginx SHALL behave as follows, each point verifiable with `curl -i`:
   1. a path that is not an existing file and has no file extension (for example `/appointments/123`) SHALL return `index.html` with `200` (SPA fallback); a missing file with an extension (for example `/missing.js`) SHALL return `404`;
   2. text responses (HTML, CSS, JS, JSON, SVG) SHALL be gzip-compressed when the client sends `Accept-Encoding: gzip`;
   3. content-hashed build assets (`*.js`, `*.css`, fonts) SHALL be sent with `Cache-Control: public, max-age=31536000, immutable`;
   4. `/`, `/index.html` and `/config.json` SHALL be sent with `Cache-Control: no-cache`, and `config.json` SHALL be `application/json`;
   5. `GET /healthz` SHALL return `200` with a short plain-text body, without access-log noise.
7. Every response, including `404` and cached assets, SHALL carry: `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` denying camera, microphone, geolocation and payment, `X-Frame-Options: DENY`, and `Cross-Origin-Opener-Policy: same-origin` (`add_header ... always`, repeated or included in every `location` that sets its own headers).
8. The CSP SHALL be `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self' <API origin>; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`. `'unsafe-inline'` for styles is recorded in Known gaps; scripts SHALL NOT need `'unsafe-inline'`: the theme script of Requirement 2.8 SHALL be allowed by its SHA-256 hash in `script-src` (computed at build) or moved to an external same-origin file.
9. The Dockerfile SHALL declare a `HEALTHCHECK` that calls `/healthz`.
10. WHEN the image is built and run with `API_BASE_URL=http://localhost:5290`, THEN `GET /config.json` SHALL return `{"apiBaseUrl":"http://localhost:5290"}` and the `Content-Security-Policy` header SHALL contain `connect-src 'self' http://localhost:5290`.

### Requirement 8: Docker Compose (no FR-ID)

**User Story:** As a developer, I want one command to serve the built SPA locally against the backend, so that I can see the production-shaped app without installing Node.

#### Acceptance Criteria

1. `docker-compose.yml` at the repository root SHALL define one service, `web`, built from the `Dockerfile`, publishing host port `8081` to container port `8080`.
2. `web` SHALL receive `API_BASE_URL` with a default of `http://localhost:5290` (`${API_BASE_URL:-http://localhost:5290}`), and the host port SHALL be overridable through `WEB_PORT` (default `8081`), without editing the file.
3. A committed `.env.example` SHALL list `API_BASE_URL` and `WEB_PORT`; `.env` SHALL be gitignored. No variable is a secret, and `docker compose up` SHALL work with no `.env` at all.
4. WHEN a developer runs `docker compose up --build`, THEN `http://localhost:8081` SHALL show the application and `docker compose ps` SHALL report the container `healthy` within 30 seconds of the image being built.
5. The compose file SHALL NOT include the backend. The README SHALL say that the backend is started from the SmartAppointments repo (`docker compose up --build` there) and that its gateway must list `http://localhost:8081` in `Cors:AllowedOrigins` (its `WEB_ORIGIN`) for browser calls to work from F1 on.
6. The container SHALL restart unless stopped (`restart: unless-stopped`) and, WHERE the base image supports it, run with a read-only root filesystem and `tmpfs` mounts for the paths nginx and the entrypoint must write.

### Requirement 9: Continuous integration (no FR-ID)

**User Story:** As a maintainer, I want every push and pull request checked the same way, so that a broken main branch is caught before merge.

#### Acceptance Criteria

1. A GitHub Actions workflow `.github/workflows/ci.yml` SHALL run on every pull request and on pushes to `main`, with `concurrency` cancelling superseded runs of the same ref and `permissions: contents: read`.
2. The jobs SHALL run in this order, each one `needs` the previous: `lint` (`pnpm lint`, `pnpm format:check`, `pnpm typecheck`) → `test` (`pnpm test` with coverage) → `build` (`pnpm build` with budgets, then `pnpm size`, uploading `dist` as an artefact) → `e2e` (installs Chromium, runs `pnpm e2e` against the built output served locally, uploads the Playwright report on failure) → `docker` (builds the image without pushing, runs it with `API_BASE_URL`, then checks `/config.json`, `/healthz`, an SPA deep link and the `Content-Security-Policy` header with `curl`).
3. Node SHALL come from `.nvmrc` (`actions/setup-node` with `node-version-file`), pnpm from the `packageManager` field (`pnpm/action-setup`), and the pnpm store SHALL be cached keyed on `pnpm-lock.yaml`.
4. Any failing step SHALL fail the workflow. A budget error, or an initial gzip size above 250 kB, SHALL fail the `build` job.
5. The workflow SHALL NOT need secrets and SHALL NOT push images. Third-party actions SHALL be pinned at least to a major version.
6. `README.md` SHALL show the CI status badge.

### Requirement 10: Documentation (no FR-ID)

**User Story:** As a developer new to the repository, I want a README and a CLAUDE.md that tell me how to run, test and extend it, so that I do not have to read the config files.

#### Acceptance Criteria

1. `README.md` SHALL state what the project is, the stack, the prerequisites (Node from `.nvmrc`, pnpm via corepack, Docker optional) and the commands: install, `pnpm start`, `pnpm test`, `pnpm lint`, `pnpm build`, `pnpm e2e` (with the Playwright browser install), `pnpm size` and `docker compose up --build`. It SHALL explain runtime configuration (`/config.json`, `API_BASE_URL`), link to the backend repo and show the CI badge.
2. `CLAUDE.md` SHALL mirror the backend's: a project status section saying what is built (initially the scaffold only, nothing feature-level) and that later phases of the plan are aspirational; the commands; the layout under `src/app`; the conventions (standalone, zoneless, signals, `OnPush`, new control flow, `inject()`, typed forms, lazy routes, Tailwind tokens rather than raw colours, Spartan helm components under `shared/ui`); the testing conventions (Vitest and Angular Testing Library queries by role, MSW for network, no zone-based helpers such as `fakeAsync`); the spec-driven loop with a pointer to `docs/specs/README.md`; the runtime-config contract; and the backend contract rules (the gateway only, error body `{status, detail}`, `X-Correlation-ID`).
3. `CLAUDE.md` SHALL carry the subagent rule used in the backend repo: delegate through the `Agent` tool on Sonnet, passing `model: "sonnet"` explicitly.
4. `README.md` and `CLAUDE.md` SHALL be updated in the same commit as any later change that makes them untrue.

## Out of scope

- **Any feature screen, route or navigation shell.** Landing, login, register, booking, appointments and admin start in F2 onwards; the layout shells are F1.
- **Authentication, token handling, interceptors and guards** (F1).
- **API types and `*ApiService`s.** `openapi-typescript`, `pnpm gen:api` and `src/app/core/api/generated/` arrive in F1. F0 only makes the API origin configurable and does not call the API.
- **The error normaliser, `AppError`, toasts and the 429 countdown** (F1).
- **Deployment beyond the container.** No registry push, hosting, domain or release pipeline; TLS is expected at an upstream proxy or platform. The image is built in CI but not published.
- **Lighthouse, accessibility audits and Playwright suites beyond one smoke test** (F6).
- **Browsers other than Chromium in Playwright**, and visual-regression testing.
- **Internationalisation, analytics and error-reporting services.**

## Known gaps

- **No coverage threshold.** Coverage is collected but not enforced until there is code worth measuring.
- **`style-src 'unsafe-inline'` in the CSP.** Angular's emitted component styles and Spartan/CDK overlays currently need it. Nonce-based styles are deferred; scripts are strict.
- **`apiBaseUrl` is only validated for shape.** The SPA cannot know the URL is the real gateway until F1 calls it; a wrong but well-formed URL shows up at the first API call, not at start.
- **CORS is a backend concern.** Until the backend's gateway-cors spec ships and `WEB_ORIGIN` is set, browser calls from the SPA (from F1 on) are blocked; F0 makes none.
- **Windows line endings.** `.gitattributes` mitigates but cannot repair a checkout made before it exists; `docker/40-config.sh` with CRLF breaks the entrypoint, so the `docker` CI job is the safety net.
- **Teal-600 is not a text colour on white.** It fails 4.5:1 (3.74:1), so the design restricts it to non-text and large-text uses.
- **Floating versions.** Because the spec does not pin Angular, Spartan or Tailwind versions, generator flags and helm output can differ from what the design assumes; the design records the actual versions at scaffold time.
