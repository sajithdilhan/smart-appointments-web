# F5 Admin console — Requirements

## Introduction

This spec builds the Admin area of the web client under `src/app/features/admin/`: a dashboard, branch management (list, create, edit, activate/deactivate, weekly schedule), service-type management, slot generation, and a command palette. It renders inside the F1 admin shell (collapsible sidebar, breadcrumbs, user menu) behind `authGuard` and `roleGuard('Admin')`, and refines build phase F5 (Part B of the approved frontend plan). It serves the backend's `FR-AVL-001` (manage branches), `FR-AVL-002` (manage service types) and `FR-AVL-003` (generate slots).

F5 **consumes** F1 and does not redefine it: `ApiClient` and the generated Availability types (`AvailabilityApiService` gets the admin methods here), `AppError` and its `kind`, `ToastService` (`showSuccess`, `handleError`), `OutageState` (including `recovered`), `SessionStore`, `roleGuard`, the shell's `breadcrumb` route data and persisted sidebar state, the zone-aware time utilities in `core/time/`, and the MSW server in `src/testing/`. Form, accessibility and error-display conventions follow F2 (visible labels, `aria-invalid` plus `aria-describedby`, errors after blur or submit, first-invalid focus, `novalidate`, double-submit protection).

Backend contract this spec relies on (verified against `Availability.Api/Controllers/`, `Availability.Application/Validations/` and `Availability.Domain/Entities/`):

- **Admin-only (`AdminPolicy`)**: `POST /api/branches`, `PUT /api/branches/{id}`, `PUT /api/branches/{id}/schedule`, `POST /api/branches/{id}/activate` and `/deactivate` (`204`, idempotent), the same set for `/api/services`, and `POST /api/slots/generate`. Reads (`GET /api/branches`, `/api/branches/{id}`, `/api/services`, `/api/services/{id}`) are open to every signed-in role; `includeInactive=true` and inactive records are honoured for an Admin only. A non-admin gets `403` on the writes.
- **Branch create** `{ code, name, description?, address, phoneNumber }` returns `201 BranchResponse { id, code, name, description, address, phoneNumber, isActive, createdAtUtc, updatedAtUtc, timeZoneId, workingHours[{ dayOfWeek, opensAt, closesAt }] }`. `code` is trimmed, must match `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,8}[A-Za-z0-9])$` (2 to 10 characters, no leading or trailing hyphen) and is stored **upper-cased** (`Branch.NormaliseCode` = `Trim().ToUpperInvariant()`). `name` required, at most 100; `description` at most 500; `address` required, at most 200; `phoneNumber` required, `^\+?[1-9]\d{1,14}$`. A duplicate code is `409` "A branch with code '{code}' already exists." Update takes the same body without `code`.
- **Schedule** `PUT /api/branches/{id}/schedule { timeZoneId, workingHours[{ dayOfWeek, opensAt, closesAt }] }`: `timeZoneId` must be an IANA id the server knows; `dayOfWeek` is the name (`"Monday"`); times are strict 24-hour `HH:mm`; each day appears at most once; `opensAt < closesAt` (one interval per day, none overnight); an **empty list is valid and closes every day**. It replaces the whole schedule and returns `200 BranchResponse` (working hours Monday-first).
- **Service type**: `code` matches `^[A-Za-z0-9](?:[A-Za-z0-9_-]{0,28}[A-Za-z0-9])$` (2 to 30 characters, hyphen and underscore inside, not at the ends) and is also stored upper-cased (`ServiceType.NormaliseCode`); `name` required at most 100; `description` at most 500; `durationMinutes` 5 to 480 and a multiple of 5. `ServiceTypeResponse { id, code, name, description, durationMinutes, isActive, createdAtUtc, updatedAtUtc }`. Duplicate code is `409` "A service type with code '{code}' already exists." Update takes everything but `code`.
- **Slot generation** `POST /api/slots/generate { branchId, serviceTypeId, fromDate, toDate, capacity }`, dates `yyyy-MM-dd`: `toDate >= fromDate`, fewer than 31 days spanned (`toDate - fromDate <= 30`), `capacity` 1 to 100. Success is `200 { createdCount, skippedCount }`. Slots are back-to-back from each day's opening interval, one service duration long, computed in the **branch's time zone**; candidates whose start is not in the future are dropped silently (counted in neither number); candidates overlapping an existing slot of that branch and service are `skippedCount`. Failures: `404` branch or service not found; `409` "Branch '{code}' is inactive." / "Service type '{code}' is inactive." / "Branch '{code}' has no working hours." (no time zone or an empty schedule) / "Slots for this branch and service type were generated by a concurrent request. Try again."; `400` validation.
- **Errors** are `{ status, detail }` as `application/problem+json`; a validation `400` has `detail` "Invalid request data. Errors: a,b" (rule messages joined with a bare comma).
- **There is no admin API** for listing appointments, staff management, reports or deleting a branch or service (out of scope).

## Decisions

Approved with these decisions and resolutions:

- **Drawers are routes.** Create and edit open as child routes (`/admin/branches/new`, `/admin/branches/:id`, `/admin/services/new`, `/admin/services/:id`) rendered in a side sheet over the still-mounted list, so every drawer is deep-linkable and Back closes it (Requirements 3, 7, 9).
- **The schedule is a page, not a drawer:** `/admin/branches/:id/schedule`.
- **The command palette belongs to the admin shell** (Ctrl/Cmd+K), built on the WAI-ARIA combobox-with-listbox pattern inside a dialog (Requirement 10).
- **"Needs attention"** lists active branches whose `timeZoneId` is null or whose `workingHours` is empty, because generation is blocked for them (Requirement 1.4).
- **"Slots generated this session"** is an in-memory counter, because the backend has no admin slot-count endpoint (Requirement 1.6).
- **Lists are loaded whole** (`includeInactive=true`, no paging parameters exist) and searched, filtered and sorted in the browser (Requirement 2.1).
- **Time-zone choices come from the browser** (`Intl.supportedValuesOf('timeZone')`) with a fallback list; the server stays the authority (Requirement 5.5).
- **Dates in the generation form are calendar dates in the selected branch's zone,** never converted through the browser zone (Requirement 8.4).
- **Upper-case preview for both branch and service codes** (the backend normalises both).
- **Past-start slots are dropped and the range cap is `to - from <= 30`,** as the backend does; the preview mirrors both (Requirement 8.5, 8.7).
- **The deactivate dialog states only guaranteed effects;** what happens to existing slots and appointments stays a Known gap.
- **Drawers are child routes over the still-mounted list** (named outlet or plain child route: the design decides); the schedule is a full page; the palette lives only in the lazy admin shell; lists load whole with client-side filter and sort.
- **No backend error codes are introduced.** Field mapping of a `400` goes by known message text in one mapping module with tests; unknown messages go to the alert (Known gap kept).
- **A zero estimate keeps Generate enabled** and shows the reason (Requirement 8.7).
- **There is no confirmation threshold on the number of slots** (a proposed 5000-slot confirmation was removed).

## Requirements

### Requirement 1: Dashboard (FR-AVL-001, FR-AVL-002, FR-AVL-003)

**User Story:** As an admin, I want one screen that shows the state of my branches and services and what needs fixing, so that I know what to do next.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin`, THEN the system SHALL render the dashboard with the title `Dashboard | Smart Appointments` and a single `<h1>` "Dashboard", and SHALL request `GET /api/branches?includeInactive=true` and `GET /api/services?includeInactive=true` in parallel.
2. The dashboard SHALL show four stat cards, each a link: "Active branches" ("{active} of {total}", to `/admin/branches`), "Inactive branches" (to `/admin/branches?status=inactive`), "Active services" ("{active} of {total}", to `/admin/services`) and "Inactive services" (to `/admin/services?status=inactive`). Each card SHALL expose its figure and label as text and read as one phrase to a screen reader, for example "Active branches: 3 of 4".
3. WHILE a request is pending, each card that depends on it SHALL show a skeleton with `aria-busy="true"`. WHEN a request fails, THEN only the cards that depend on it SHALL show an inline error with a **Retry** button (not a toast), and the other cards SHALL stay visible.
4. The dashboard SHALL show a "Needs attention" list of every **active** branch whose `timeZoneId` is null or whose `workingHours` is empty, each row naming the branch (name and code) with a "Set schedule" link to `/admin/branches/:id/schedule`. IF the list is empty, THEN it SHALL show "Every active branch has a schedule." and no list.
5. The dashboard SHALL show "Quick actions" with links "New branch" (`/admin/branches/new`), "New service" (`/admin/services/new`) and "Generate slots" (`/admin/slots`). WHEN there is no active branch or no active service, THEN "Generate slots" SHALL remain a link but carry a note naming what is missing ("Create an active branch first").
6. The dashboard SHALL show "Slots generated this session" from an in-memory `SlotActivityStore` (the sum of `createdCount` of successful generations since the page was loaded), labelled "this session" with a note that it resets on reload. IF no generation has happened, THEN it SHALL show "No slots generated yet" instead of 0, and no figure SHALL imply a backend total.
7. WHEN `OutageState.recovered` increments, THEN the dashboard SHALL reload both lists.
8. The stat cards SHALL stack in one column below 640 px and two columns below 1024 px, with no horizontal scroll down to 320 px.

### Requirement 2: Branches list (FR-AVL-001)

**User Story:** As an admin, I want to find any branch quickly and see its status at a glance, so that I can manage it without scrolling through everything.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin/branches`, THEN the system SHALL render the title `Branches | Smart Appointments`, a single `<h1>` "Branches" and a "New branch" link-button to `/admin/branches/new`, and SHALL load `GET /api/branches?includeInactive=true` once. Search, filter and sort SHALL run in the browser without further requests.
2. The list SHALL be a data table (`<table>` with `<caption>`, `<th scope="col">`) with columns Code, Name, Phone, Status, Schedule and Actions. Status SHALL be a badge with the text "Active" or "Inactive" and an icon (never colour alone). Schedule SHALL show the time zone and the number of open days ("Asia/Colombo, 5 days open"), or "Not set" with a warning icon WHEN `timeZoneId` is null or `workingHours` is empty.
3. A search box labelled "Search branches" SHALL filter on a case-insensitive substring of code, name, address or phone while typing (debounced to no more than 150 ms), combined with a status filter "All", "Active", "Inactive". Search text and filter SHALL be mirrored in the URL (`?q=`, `?status=`) so a view can be shared and reloaded; an unknown `status` value SHALL act as "All".
4. The Code and Name column headers SHALL be buttons that sort ascending, descending, then back to the default (name ascending); the active sort SHALL be exposed with `aria-sort` on the `<th>`. Sorting SHALL be case-insensitive, locale-aware (`Intl.Collator`) and stable.
5. Each row SHALL offer Edit (to `/admin/branches/:id`), Schedule (to `/admin/branches/:id/schedule`) and Activate or Deactivate (whichever applies, Requirement 4), with accessible names that include the branch name ("Edit Colombo Central"). On narrow viewports the actions MAY collapse into a labelled, keyboard-operable menu.
6. WHILE the request is pending, the table SHALL show skeleton rows with `aria-busy="true"`. IF it fails, THEN the page SHALL show an inline error with the F1 message and a **Retry** button instead of a table. IF there are no branches, THEN it SHALL show "No branches yet" with a "New branch" button; IF the filters match nothing, THEN "No branches match your filters" with a **Clear filters** button.
7. WHEN the filtered count changes, THEN a visually hidden `role="status"` region SHALL announce "{n} branches shown" once per settled change (debounced, not per keystroke).
8. WHILE the viewport is narrower than 768 px, the table SHALL render as one card per branch with the same fields and actions, and sorting SHALL be available through a labelled select; no horizontal page scroll down to 320 px.
9. WHEN `OutageState.recovered` increments, THEN the list SHALL reload. After a successful mutation of Requirements 3 to 5, the affected row SHALL update from the response or a refetch without a full reload and without losing search, filter, sort or scroll position.

### Requirement 3: Branch create and edit drawer (FR-AVL-001)

**User Story:** As an admin, I want to add or change a branch in a side panel, so that I keep my place in the list.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin/branches/new` or `/admin/branches/:id` (from the list or by deep link), THEN the system SHALL render a side drawer (`role="dialog"`, `aria-modal="true"`, labelled by its heading "New branch" or "Edit branch") over the list, with the title `New branch | Smart Appointments` or `Edit branch | Smart Appointments` and focus on the first field. WHILE open, focus SHALL be trapped. WHEN it closes (Escape, a Close button, the backdrop or the browser Back button), THEN the route SHALL return to `/admin/branches` keeping the list's query parameters and focus SHALL return to the control that opened it, or to the page heading when opened by deep link.
2. The drawer SHALL contain, in order, with visible labels: Code (create only), Name, Description (textarea, optional), Address, Phone number. Below 640 px the drawer SHALL fill the width.
3. WHEN editing, THEN the Code SHALL be shown as read-only text with the hint "The code cannot be changed after creation" and SHALL NOT be sent in the body.
4. The client SHALL validate with rules defined once in a pure function (used by the form and its unit tests), mirroring the backend:
   - code (create): after trimming, non-empty ("Code is required.") and matching `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,8}[A-Za-z0-9])$` ("Code must be 2-10 letters, digits or hyphens, and cannot start or end with a hyphen."); hint "Letters, digits and hyphens; saved in upper case", with a live preview of the normalised value ("Will be saved as COL-01");
   - name: required ("Name is required."), at most 100 ("Name cannot exceed 100 characters.");
   - description: at most 500 ("Description cannot exceed 500 characters."), with a remaining-characters counter that is not announced per keystroke;
   - address: required ("Address is required."), at most 200 ("Address cannot exceed 200 characters.");
   - phone number: required ("Phone number is required.") and, after removing spaces, dashes and parentheses, matching `^\+?[1-9]\d{1,14}$` ("Enter the number in international format, for example +14155550123."); the cleaned value SHALL be sent.
5. Field errors SHALL follow F2 Requirement 3.7 (after blur or an attempted submit, under the field, `aria-invalid`, `aria-describedby`, cleared when valid). WHEN a submit is attempted while any field is invalid, THEN the system SHALL NOT call the API and SHALL focus the first invalid field.
6. WHEN the form is valid and submitted, THEN the system SHALL call `POST /api/branches` (create) or `PUT /api/branches/{id}` (edit) once with trimmed values (an empty description sent as `null`). WHILE pending, Save SHALL be disabled with a spinner and `aria-busy="true"`, the fields read-only, and a second submit SHALL NOT start a second call.
7. WHEN create returns `201`, THEN the system SHALL close the drawer, add the branch to the list, and show a toast "Branch {code} created" with a "Set schedule" action (link to the schedule page). WHEN update returns `200`, THEN it SHALL close the drawer and toast "Branch updated".
8. IF create returns `409`, THEN the system SHALL show "A branch with code {CODE} already exists." under the Code field (the normalised code), set `aria-invalid`, focus it, keep every typed value and NOT toast.
9. IF the API returns `400` with `detail` "Invalid request data. Errors: ...", THEN the system SHALL split the message list (matching known backend messages by their text first, because some of them contain commas themselves), map each message equal to a known backend rule message to its field, show those under the fields, and show any unmapped message in a `role="alert"` region at the top of the form; all values SHALL be kept and focus SHALL move to the first mapped field or the region.
10. IF edit returns `404`, THEN the system SHALL close the drawer, toast "That branch no longer exists" and reload the list. IF the deep link names an unknown id, THEN the drawer SHALL show a not-found state with a "Back to branches" link (not the global 404 page).
11. IF the call fails with a network error, timeout or `502`/`503`/`504`, THEN the form SHALL stay open with its values, re-enable, and rely on the F1 outage banner. IF it fails with `429`, THEN Save SHALL be disabled with the F1 `RateLimitNotice`.
12. The unsaved-changes guard (Requirement 11) SHALL apply to the drawer.

### Requirement 4: Branch activate and deactivate (FR-AVL-001)

**User Story:** As an admin, I want to close or reopen a branch with a clear warning about what that does, so that I do not hide a branch by accident.

#### Acceptance Criteria

1. WHEN an Admin chooses Deactivate on an active branch, THEN the system SHALL open a confirmation dialog (`role="alertdialog"`, labelled and described, initial focus on **Cancel**) titled "Deactivate {name}?" stating that: customers will no longer see this branch or search its slots; admins still see it; slot generation for it is blocked until it is reactivated; and that existing appointments and already generated slots are not cancelled or removed by this action. The confirm button SHALL read "Deactivate branch".
2. WHEN an Admin chooses Activate on an inactive branch, THEN a lighter confirmation "Activate {name}?" SHALL state that it becomes visible to customers again, with the confirm button "Activate branch". IF the branch has no schedule, THEN the dialog SHALL add "This branch has no schedule, so no slots can be generated until you set one" with a link to the schedule page.
3. WHEN the admin confirms, THEN the system SHALL call `POST /api/branches/{id}/deactivate` or `/activate` once. WHILE pending, the confirm button SHALL be disabled with `aria-busy="true"` and the dialog SHALL stay open. WHEN it returns `204`, THEN the dialog SHALL close, the row's badge and action SHALL update, a toast "{name} is now inactive" or "{name} is now active" SHALL show, and focus SHALL return to that row's action button.
4. WHEN the admin cancels (button, Escape or backdrop), THEN no request SHALL be sent and focus SHALL return to the triggering button.
5. IF the call fails with `404`, THEN the dialog SHALL close and the list reload with the toast "That branch no longer exists". IF it fails otherwise, THEN the dialog SHALL stay open with the F1 message inline so the admin can retry or cancel.
6. The same flow SHALL be available from the edit drawer header, and the badge there SHALL update too.
7. Because both endpoints are idempotent (`204` whether or not the state changed), the toast wording SHALL stay neutral as in criterion 3 and SHALL NOT claim this admin changed the state.

### Requirement 5: Branch schedule editor (FR-AVL-001, FR-AVL-003)

**User Story:** As an admin, I want to set a branch's time zone and weekly opening hours in one grid, so that slots can be generated for it.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin/branches/:id/schedule`, THEN the system SHALL load `GET /api/branches/{id}` and render the title `Schedule | Smart Appointments`, a single `<h1>` "Schedule for {name}", breadcrumbs (Dashboard, Branches, {name}, Schedule) and a back link to the list. IF the id is unknown, THEN a not-found state with a link to the list SHALL show; IF the branch is inactive, THEN the editor SHALL still work and show a note that the branch is inactive.
2. The editor SHALL show a **weekly grid**, Monday first, one row per day with: the day name, an "Open" switch (`role="switch"`, name "Open on Monday") and, WHEN open, "Opens" and "Closes" time inputs (24-hour `HH:mm`, 5-minute step, labelled "Monday opens", "Monday closes"). A closed day SHALL show "Closed" and no active time inputs. The state SHALL be initialised from the response (days absent from `workingHours` are closed).
3. The client SHALL validate before saving, with messages under the row: both times required on an open day ("Enter an opening and a closing time."), format `HH:mm` ("Use a 24-hour time such as 09:00."), and opens strictly before closes ("Opening time must be before closing time."). The page SHALL state that one interval per day is supported and that it cannot cross midnight. A day SHALL never appear twice in the request.
4. A "Copy Monday to weekdays" button SHALL copy Monday's open state and times to Tuesday through Friday (toast "Copied Monday's hours to Tuesday to Friday"), SHALL leave Saturday and Sunday unchanged, and SHALL be disabled WHEN Monday is closed or invalid. A "Close all days" action SHALL close every day.
5. The time-zone field SHALL be a searchable combobox (`role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`, `aria-autocomplete="list"`; ArrowUp and ArrowDown move, Enter selects, Escape closes; typing filters by case-insensitive substring treating `_` and space alike) over `Intl.supportedValuesOf('timeZone')`, falling back to a built-in list of common IANA ids WHERE that function is unavailable. Each option SHALL show the identifier and its **current UTC offset** ("Asia/Colombo, UTC+05:30"), computed with `Intl.DateTimeFormat` for the present instant. The selected value SHALL show its offset. Only listed values SHALL be accepted and the field SHALL be required ("Choose a time zone.").
6. WHEN the branch has no time zone yet, THEN nothing SHALL be preselected, but the browser's zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) SHALL be offered as the first option labelled "Your browser's zone".
7. WHEN the form is valid and the admin saves, THEN the system SHALL call `PUT /api/branches/{id}/schedule` once with `{ timeZoneId, workingHours }` listing only open days in Monday-first order, `dayOfWeek` as the English name and times as `HH:mm`. WHILE pending, Save SHALL be disabled with `aria-busy="true"` and the grid read-only. WHEN it returns `200`, THEN the editor SHALL take the response as its new state, toast "Schedule saved" and become pristine.
8. WHEN the admin saves with every day closed, THEN a confirmation SHALL first explain that the branch will have no working hours and slot generation will be blocked until a schedule is set; saving SHALL proceed only on confirmation.
9. IF the API returns `400`, THEN the messages SHALL show in a `role="alert"` region with all values kept. IF `404`, THEN Requirement 3.10 applies. Network, outage and `429` handling follows Requirement 3.11.
10. The page SHALL carry the note "Changing the schedule affects only slots generated from now on. Existing slots stay as they are."
11. The unsaved-changes guard (Requirement 11) SHALL apply. Every control SHALL be keyboard operable, and below 768 px the grid SHALL collapse to one card per day.

### Requirement 6: Service types list (FR-AVL-002)

**User Story:** As an admin, I want to see and filter the service catalogue with durations and status, so that I can manage what customers can book.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin/services`, THEN the system SHALL render the title `Services | Smart Appointments`, a single `<h1>` "Services", a "New service" link-button (to `/admin/services/new`) and a data table with columns Code, Name, Duration, Status and Actions, loaded once from `GET /api/services?includeInactive=true`.
2. The list SHALL provide the behaviour of Requirement 2.2 to 2.9 with "services" for "branches": search (code, name, description), status filter mirrored in `?q=` and `?status=`, sortable Code, Name and Duration headers, badges, announced count, loading, error, empty and no-match states, and the mobile card layout. Duration SHALL read "45 min", and "1 h 30 min" from 60 minutes.
3. Each row SHALL offer Edit (to `/admin/services/:id`) and Activate or Deactivate. Deactivate SHALL confirm that customers can no longer select this service, that existing appointments are not changed and that slot generation for it is blocked; Activate SHALL use the lighter confirmation. Calls, pending state, `404` and failure handling follow Requirement 4.3 to 4.7 against `/api/services/{id}/activate|deactivate`.

### Requirement 7: Service create and edit drawer (FR-AVL-002)

**User Story:** As an admin, I want to define a service with its duration in friendly steps, so that slot lengths are right.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin/services/new` or `/admin/services/:id`, THEN the system SHALL render a drawer behaving as Requirement 3.1, 3.5, 3.6 and 3.8 to 3.12 (titles `New service | Smart Appointments`, `Edit service | Smart Appointments`), with fields Code (create only, read-only on edit), Name, Description and Duration.
2. The client SHALL validate with a pure function mirroring the backend: code after trimming non-empty ("Code is required.") and matching `^[A-Za-z0-9](?:[A-Za-z0-9_-]{0,28}[A-Za-z0-9])$` ("Code must be 2-30 letters, digits, hyphens or underscores, and cannot start or end with a hyphen or underscore."), saved upper-case with a preview; name required, at most 100; description at most 500; duration an integer 5 to 480 ("Duration must be between 5 and 480 minutes.") and a multiple of 5 ("Duration must be a multiple of 5 minutes.").
3. Duration SHALL be a **stepper**: a numeric input (`inputmode="numeric"`) with "Decrease" and "Increase" buttons changing the value by 5 (clamped at 5 and 480, buttons disabled at the bounds), ArrowUp and ArrowDown as the same steps, a visible unit "minutes" and an echo in hours ("1 h 30 min"). A typed value that is not a multiple of 5 SHALL NOT be silently rounded; it SHALL show the validation message after blur.
4. The drawer SHALL offer **preset chips** for 15, 30, 45, 60, 90 and 120 minutes, each a toggle button with `aria-pressed` true WHEN it equals the current value. Activating one SHALL set the value and keep focus on the chip; the chips and the stepper SHALL update each other.
5. WHEN create returns `201`, THEN the drawer SHALL close and a toast "Service {code} created" SHALL offer "Generate slots" (to `/admin/slots?serviceId={id}`). `409` SHALL show "A service with code {CODE} already exists." under Code.
6. The edit drawer SHALL note "Changing the duration affects only slots generated from now on. Existing slots keep their length."

### Requirement 8: Slot generation (FR-AVL-003)

**User Story:** As an admin, I want to generate slots for a branch and service over a date range, with a preview of what I am about to create, so that customers can book.

#### Acceptance Criteria

1. WHEN an Admin opens `/admin/slots`, THEN the system SHALL render the title `Generate slots | Smart Appointments`, a single `<h1>` "Slot generation" and a form with Branch, Service, From date, To date, Capacity, a live preview, a Generate button and a result area. `?branchId=` and `?serviceId=` SHALL preselect a picker WHEN they name an active record, and SHALL be ignored silently otherwise.
2. The pickers SHALL load both lists with `includeInactive=true` and make **only active** records selectable, labelled "{name} ({code})". Inactive records SHALL NOT be selectable; a note "Inactive branches and services are not listed. Reactivate one to generate slots for it." SHALL link to `/admin/branches?status=inactive` and `/admin/services?status=inactive`. IF there is no active branch or no active service, THEN the form SHALL show an empty state naming what is missing with a link to create or activate one, and Generate SHALL be disabled.
3. WHEN the selected branch has no `timeZoneId` or an empty `workingHours`, THEN the system SHALL show "This branch has no schedule, so slots cannot be generated" with a **Set a schedule** link to `/admin/branches/:id/schedule` and SHALL disable Generate (the condition the backend answers with `409`).
4. Dates SHALL be calendar dates (`yyyy-MM-dd`) read in the **selected branch's time zone**: the label SHALL say so ("Dates are in Asia/Colombo (UTC+05:30)"), the earliest From date SHALL be today **in that zone** (via the F1 time utilities, not `new Date(string)`), the date inputs SHALL be disabled with a hint until a branch is chosen, and the chosen strings SHALL be sent unchanged.
5. The range SHALL be capped: To not before From ("From date cannot be after to date.") and a span of at most 31 days, that is `To - From <= 30` days ("The date range cannot span more than 31 days."), enforced in the picker (later dates disabled) and in validation. Quick ranges "Next 7 days", "Next 14 days" and "Next 30 days", counted from today in the branch zone, SHALL fill both dates.
6. Capacity SHALL be an integer 1 to 100 ("Capacity must be between 1 and 100."), default 1, with the hint "How many customers can book the same slot."
7. The **preview** SHALL update as inputs change and read "{N} days, about {M} slots estimated" (singular for one day), computed locally from the branch's weekly schedule and the service duration: per date in the range, floor(open-interval minutes / duration) for an open weekday, 0 for a closed one, summed; N is the number of dates in the range. A secondary line SHALL state the number of closed days in the range. WHEN today (in the branch zone) is in the range, THEN it SHALL add "slots that have already started today are not created". It SHALL be labelled an estimate (the server's `createdCount` is authoritative, because it also skips overlaps), and SHALL sit in a polite `role="status"` region updated debounced, not per keystroke. IF the estimate is 0, THEN it SHALL say "No slots would be created: the branch is closed on every day in this range"; Generate SHALL stay enabled (the server decides) but the page SHALL show that message.
8. WHEN the form is valid and submitted, THEN the system SHALL call `POST /api/slots/generate` once with `{ branchId, serviceTypeId, fromDate, toDate, capacity }`. WHILE pending, the button SHALL be disabled with a spinner and `aria-busy="true"`, the fields read-only, and a second submit SHALL NOT start a second call.
9. WHEN it returns `200`, THEN a **result card** in a `role="status"` region SHALL show, with focus on its heading, "{createdCount} slots created" and "{skippedCount} skipped because they overlap existing slots", the branch, service and range, and a "Generate more" action (resets the dates, keeps the pickers). `createdCount` SHALL be added to `SlotActivityStore`. IF both counts are 0, THEN the card SHALL explain that nothing was created (closed days, or every slot already in the past) instead of reporting plain success.
10. A `404` or `409` SHALL be explained in an inline `role="alert"` region above the form (never only a toast), with a link that fixes the cause. Matching on status and `detail` text: "has no working hours" becomes "This branch has no schedule" with **Set a schedule**; "Branch '…' is inactive." becomes "This branch is inactive" with **Activate it** (to `/admin/branches?status=inactive`); "Service type '…' is inactive." becomes "This service is inactive" with **Activate it** (to `/admin/services?status=inactive`); the concurrent-generation `409` becomes "Another generation for this branch and service was running at the same time. Check the result and try again." with a **Try again** button (never retried automatically); `404` becomes "That branch no longer exists" or "That service no longer exists" and the pickers reload. A `409` matching no pattern SHALL show the server `detail` unchanged.
11. A `400` SHALL map known messages to the date and capacity fields as in Requirement 3.9 and show the rest in the alert region. Network, outage and `429` handling follows Requirement 3.11.
12. The unsaved-changes guard (Requirement 11) SHALL apply once any field differs from its initial value and no successful generation has reset it.

### Requirement 9: Admin routes and deep links (no FR-ID)

**User Story:** As an admin, I want every admin screen and drawer to have its own URL, so that I can bookmark, share and refresh them.

#### Acceptance Criteria

1. The admin routes SHALL be lazy children of the F1 admin shell, each with a `title` and a `breadcrumb` data entry: `/admin`, `/admin/branches`, `/admin/branches/new`, `/admin/branches/:id`, `/admin/branches/:id/schedule`, `/admin/services`, `/admin/services/new`, `/admin/services/:id`, `/admin/slots`. They SHALL replace the F1 placeholders for `/admin`, `/admin/branches`, `/admin/services` and `/admin/slots`.
2. The drawer routes SHALL be children of their list route and render in a named outlet over the list, so the list stays mounted behind it, keeps its state and is not reloaded when the drawer closes unless data changed.
3. A `:id` that is not a GUID SHALL show the not-found state of Requirement 3.10 without sending a request.
4. The F1 sidebar SHALL mark the active section with `aria-current="page"` for a list route and its drawer children alike, and the F1 route announcer SHALL announce a drawer's title when it opens.
5. F5 SHALL add no client role logic beyond F1's `roleGuard`. A `403` from any admin call SHALL surface through the F1 `handleError` toast without ending the session.

### Requirement 10: Command palette (no FR-ID)

**User Story:** As an admin, I want to jump to any admin action from the keyboard, so that I can work quickly without hunting through menus.

#### Acceptance Criteria

1. WHILE the user is in the admin shell, WHEN they press `Ctrl+K` or `Cmd+K`, THEN the system SHALL open the palette and prevent the browser default for that chord. A visible "Search or jump to" button in the shell's top bar SHALL open it too (discoverable, usable on touch) and show the shortcut with the platform's key name. The shortcut SHALL NOT fire while another modal is open.
2. The palette SHALL be a modal dialog (`role="dialog"`, `aria-modal="true"`, labelled "Command palette") with a search input implementing the WAI-ARIA combobox pattern (`role="combobox"`, `aria-expanded="true"`, `aria-controls` to a `role="listbox"`, `aria-autocomplete="list"`, `aria-activedescendant` naming the highlighted `role="option"`), focus on the input, trapped focus, and focus returned to the previous element on close.
3. The palette SHALL offer: **Go to Dashboard**, **Go to Branches**, **Go to Services**, **Go to Slot generation**; **New branch** (`/admin/branches/new`), **New service** (`/admin/services/new`), **Generate slots** (`/admin/slots`); **Toggle theme** and **Sign out**. WHERE the branch and service lists are already in memory, it SHALL also offer "Edit branch: {name}", "Edit schedule: {name}" and "Edit service: {name}" entries (at most 50 shown) without issuing its own request.
4. WHEN the user types, THEN results SHALL filter by a case-insensitive match of every typed word against label and keywords, ranking an exact prefix first, grouped (Navigate, Create, Records, Settings) with group headings that are not options. WHEN nothing matches, THEN "No matching commands" SHALL show in a `role="status"` region.
5. ArrowDown and ArrowUp SHALL move the highlight (wrapping), Home and End the first and last option, Enter SHALL run the highlighted command, Escape SHALL close, and a click SHALL run an option. The highlighted option SHALL be distinguishable by more than colour and scrolled into view; typing SHALL NOT move focus off the input.
6. WHEN a command runs, THEN the palette SHALL close, then navigate or act, and focus SHALL land per the destination (the drawer's first field or the page heading). A command whose target is the current route SHALL close the palette and change nothing.
7. A visually hidden `role="status"` region SHALL announce the result count when it changes ("5 results"), debounced.
8. The palette SHALL respect `prefers-reduced-motion`, meet AA contrast in both themes, fill the width below 640 px and make no network request of its own.
9. The palette and its key listener SHALL live in the lazy admin feature, SHALL NOT be present for other shells, and SHALL be removed when the admin shell is destroyed.
10. The command registry SHALL be a pure, unit-tested data module (id, label, keywords, group, action), so filtering, ranking and grouping are testable without the DOM.

### Requirement 11: Unsaved-changes guard (no FR-ID)

**User Story:** As an admin, I want a warning before I lose what I typed, so that a stray click does not discard my work.

#### Acceptance Criteria

1. A form of this spec (branch drawer, service drawer, schedule editor, slot generation form) SHALL be "dirty" WHEN its values differ from the last loaded or saved values, and pristine again WHEN they are equal or a save succeeds.
2. WHEN a dirty form is left through the router (sidebar link, palette command, Back, drawer close), THEN a functional `canDeactivate` guard SHALL open an `alertdialog` "Discard changes?" ("You have unsaved changes. They will be lost.") with **Keep editing** (default, initial focus) and **Discard changes**. Keep editing SHALL cancel the navigation; Discard SHALL continue it.
3. WHILE a form is dirty, a `beforeunload` handler SHALL ask the browser to confirm a tab close, reload or leaving the site, and SHALL be removed when pristine or destroyed.
4. WHEN a dirty drawer's Close button, Escape or backdrop is used, THEN the same confirmation SHALL appear first; a pristine drawer SHALL close immediately.
5. The navigation a successful save performs itself (closing the drawer) SHALL NOT trigger the guard.
6. The dialog SHALL trap focus and be keyboard operable; two simultaneous guarded exits SHALL show one dialog.
7. A unit test per form SHALL cover: pristine navigation passes, dirty navigation is blocked until confirmed, the dialog outcome decides.

### Requirement 12: Accessibility and responsive behaviour (no FR-ID)

**User Story:** As an admin using a keyboard, a screen reader or a phone, I want the console to be fully usable, so that no task depends on a mouse or a wide screen.

#### Acceptance Criteria

1. Every page SHALL have one `<h1>`, one `<main>` (from F1), and a title `<Page> | Smart Appointments` via the route `title`. WHEN the route or drawer changes, THEN focus SHALL move to the page's `<h1>` (`tabindex="-1"`) or the drawer's first field and the F1 announcer SHALL announce the new title.
2. ## Out of scope

- **Staff management, reports and appointment oversight** (listing, searching or cancelling any customer's appointment): the backend has no admin API for them (FR-BKG-004, FR-BKG-006; the Queue, Notification and Reporting services do not exist). The dashboard shows only branch, service and schedule state, never appointment counts or revenue.
- **Deleting a branch or service:** there is no `DELETE` endpoint, deactivation is the only removal, and no "Delete" control appears anywhere.
- **Bulk operations** (multi-select, import, clone) and CSV import or export.
- **Viewing, editing or deleting individual slots,** regenerating slots, or any view of slot occupancy: no admin slot endpoint exists besides `generate`.
- **Schedule exceptions** (holidays, split shifts, overnight intervals): the backend models one interval per weekday.
- **A per-generation duration:** the length is always the service type's duration.
- **User and role management** and **audit trails** of admin actions.
- **Server-side paging, sorting or search:** the API offers none.
- **Persisting "slots generated this session"** or any admin preference other than the F1 sidebar state.
- **Internationalisation:** English only; dates and zones follow the browser locale through the F1 utilities.

## Known gaps

- **The 400 split is brittle.** The server joins failed rules with a bare comma, so a message containing one cannot be split reliably. Requirements 3.9 and 8.11 map only messages the client itself knows and show the rest in an alert. Client validation mirrors the backend so this path is rare.
- **Deactivating does not cancel or hide existing slots and appointments.** The backend flips `IsActive` only. Whether slots already generated for an inactive branch stay searchable or bookable is backend behaviour this spec neither changes nor promises; the confirmation wording (Requirements 4.1, 6.3) says only what the contract guarantees. To be verified against the search and booking handlers during design.
- **Schedule and duration changes do not touch existing slots.** An admin who wants new lengths must generate again, and overlapping candidates are skipped, so old-length slots can block new ones.
- **The preview is an estimate.** It cannot know existing overlaps, daylight-saving gaps or folds in the branch zone, or the server's "already started" cut-off; `createdCount` is authoritative.
- **The browser's IANA list may differ from the server's tzdata.** A zone the server rejects is a `400` shown in the alert; a zone the browser lacks cannot be chosen; the offset shown is the browser's rule.
- **"Today in the branch zone" uses the browser clock.** A wrong clock shifts the earliest selectable date by up to a day; the server's rule is the authority.
- **Concurrent edits are last-write-wins.** Branches and services have no version or `ETag`; the schedule `PUT` replaces the whole schedule.
- **Lists are not paged.** Every load fetches every branch and service; fine for a portfolio dataset, not for thousands of records.
- **Palette record entries are only as fresh as the lists already loaded** in this session.
- **Role checks are client convenience only.** `roleGuard('Admin')` hides screens; the services enforce `AdminPolicy` and answer `403` (F1 Known gaps).
- **CI does not exercise the real Availability service.** Verification is MSW and mocked Playwright; the manual check of Requirement 13.6 is the only end-to-end proof until a Compose-backed e2e job exists.
- **Negative-DST zones.** For ambiguous local times in zones with negative DST (for example Europe/Dublin), the preview may resolve differently from the backend on Linux; `createdCount` is authoritative.
